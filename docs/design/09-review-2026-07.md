Post-publication review of `scanr` at 38 commits, 315 tests, CI green.

Each finding is labelled by evidence: **demonstrated** (reproduced with a command),
**measured** (from a tool), or **by inspection** (read from the code, not executed).

## Integrity findings

These matter more than the rest because each one weakens the guarantee the tool is built
on — that the record always says what happened.

### C1 — A panicking worker is reported as a natural completion
**By inspection** · `run.rs:314`

`let _ = h.join()` discards the join result. `panic = "unwind"` is deliberate (D1) so a
panicking worker cannot stop the writer — but nothing then notices that it died.

Tracing the consequence: the worker's channel clone drops, the collector eventually sees
a disconnect and exits normally, `counts.started` still includes the probe the dead worker
took, and `writer_error` is unset and `cancel` unset — so the terminal event is
`scan_completed` with `termination: "natural"` and `graceful: true`, and the process exits
0.

It is not fully silent: `abandoned` will be non-zero, and `verify` still passes because
`planned == completed + abandoned + not_started` continues to hold. But a consumer
checking the terminal event type — the thing the specification tells them to trust — is
told the scan finished normally when a thread crashed.

### C2 — Writer failures on non-probe events are discarded
**By inspection** · `run.rs:118, 129, 227, 291`

Only `probe_result` records a write failure into `writer_error`. `target_resolved`, the
plan warnings, the runtime pressure warnings, and `scan_progress` all use
`let _ = writer.emit(...)`.

So a disk filling while warnings are being written produces a record that is missing
events, with a `scan_completed` terminal and exit 0. The M4 milestone specifically
promised that writer failure is detected; it is detected for one event type out of six.

### C3 — `verify` accepts impossible values, and `remainder` then truncates them
**Demonstrated**

`verify` checks structure — ordering, sequence, counts, terminal-event uniqueness,
credentials — but no field *values*. A record containing `"port": 65616`:

```console
$ scanr output verify /tmp/badport.jsonl
  ok — record is complete and internally consistent
```

`remainder` then reads that port with `p as u16` (`verify.rs:484`), truncating 65616 to
80, concluding port 80 was already probed, and reporting nothing outstanding. A resume
driven by that output silently skips endpoints.

Two defects compounding: no value validation, and a lossy cast where `u16::try_from`
belongs. Fuzzing did not catch it because neither step panics.

## Product findings

### F1 — A resumed scan cannot be linked to what it resumed
**Demonstrated**

`scan_config` for a `--pairs` scan carries no parent identifier:

```
scan_config keys: description, dns, host, output, permutation, ports,
                  probes_planned, profile, provenance, scan_id, scan_name,
                  targets, timing, transport
any link to a prior scan? False
```

The original brief asked "how resumed scans link to prior scan IDs". That question was
never answered — `resume` was replaced by `remainder` (D12) and the linkage question went
with it. The result is that a scan split across an interruption produces two records that
cannot be connected except by a human remembering.

For a tool whose value proposition is a forensic record, that is the most substantive gap
found in this review.

## Maintainability findings

### M1 — Three functions hold most of the complexity
**Measured** · `resolve` 318 lines, `execute` 270, `validate` 262; 23 functions over 60

These are also the least-covered and the ones hiding C1 and C2. All three are already
sectioned by comment banners, so the seams exist; they simply have not been cut.

### M2 — There is no encapsulation boundary
**Measured** · 16 `pub mod`, including `testsupport`

Every internal module is public API, and the in-process fixture servers ship in the
library surface. Harmless while `publish = false`, but it means nothing signals what is
internal, and any refactor is nominally breaking.

### M3 — Spec drift is guarded for two specs out of three
**Demonstrated**

The JSONL specification and the man pages both have drift tests that fail the build.
`docs/design/06-cli-spec.md` has none, and has drifted: no mention of `--pairs` or
`--calibrate`, and a diff against `--help` shows several more flags missing. The
*user-facing* documentation covers them; the design spec does not.

## Polish findings

### P1 — Pair-scan `plan` output reads badly
**Demonstrated**

```
targets         2 (3 explicit host:port pairs)
ports           3 ((explicit pairs))
```

Double parentheses, a target count sitting next to a pair count, and no explicit
statement that this is a pair scan. `plan` is a headline surface — "look before you
scan" — so it should not be the roughest output in the tool.

### P2 — Error composition produces a nonsense sentence
**Demonstrated**

```console
$ scanr plan --pairs cidr.txt
error: `10.0.0.0/24:80 (a pair must name a single host, not a range or CIDR)` is not a
valid IP address, CIDR block, range, or hostname
```

`parse_pair` stuffs its explanation into `TargetParseError::Malformed`, whose `Display`
wraps the payload in backticks and appends its own clause. It needs its own variant.

# Plan

Ordered so that each phase is protected by the tests from the one before it. R1 and R3
are deliberately adjacent: fixing the integrity defects properly requires a way to inject
failure, which is the same seam R3 needs.

## R1 — Integrity defects

**Scope**

* **C1**: collect join results; a panicked worker emits a `scan_warning` with a new
  `worker_panic` code and forces the terminal event to `scan_failed`. Add `worker_panics`
  to the terminal counts so the record states it numerically.
* **C2**: route every `emit` through one helper that records the first failure into
  `writer_error`, so no event type can fail silently. Removes the asymmetry rather than
  patching each call site.
* **C3**: `remainder` uses `u16::try_from` and treats an out-of-range port as a record
  error rather than truncating. `verify` gains value validation — port in `1..=65535`,
  `state` and `source` within their enums, `attempts >= 1`, non-negative timings,
  `probe_index < probes_planned`, `ts` parseable.

**Tests** A transport that panics on demand; `RLIMIT_FSIZE` tuned to fail during the
warning phase rather than mid-results; a record with an out-of-range port must fail
`verify` and must not silently shrink `remainder`.

**Done when** each of the three has a test that fails before the fix.

## R2 — Resume provenance

**Scope** `output remainder` emits a leading `# resumed-from: <scan-id>` comment;
`--pairs` parses it and records `resumed_from` in `scan_config`. A `--resumed-from <id>`
flag covers the manual case. `verify` reports the link when present.

The pipe therefore carries provenance with no extra user action:
`scanr output remainder x.jsonl | scanr run --pairs -`.

**Done when** two records from an interrupted-then-resumed scan can be chained
programmatically, and the JSONL spec documents the field. Closes the open question from
the original brief.

## R3 — Cover the failure paths

**Scope** Introduce a seam so `execute()` can be driven in-process with an injected
transport and writer, instead of only through a spawned binary. Then cover: worker panic,
writer failure at each event type, forced (second-signal) shutdown, and the drain-budget
expiry.

Add `cargo llvm-cov` to CI with a floor — 85% to start, since the current combined figure
is 86.7% — so coverage cannot silently regress.

**Done when** `run.rs` region coverage is above 90% and the floor is enforced.

## R4 — Reduce the three complexity hotspots

**Scope** Split along the comment banners that are already there: `resolve()` into
transport → profile → timing → dns → targets/ports → scalars → warnings; `execute()` into
setup → collect → finalize; `validate()` per config section. No behaviour change.

Deliberately after R1–R3 so the new tests protect the refactor.

**Done when** no function outside tests exceeds ~120 lines and the suite is unchanged.

## R5 — API surface and the third drift guard

**Scope** Narrow the library to a deliberate public surface, `pub(crate)` for the rest,
and put `testsupport` behind a feature flag. Add a CLI-spec drift test mirroring the
existing JSONL and man-page ones, then bring `06-cli-spec.md` back in line.

**Done when** the CLI spec cannot drift without failing the build.

## R6 — Polish

**Scope** Pair-scan `plan` rendering (an explicit `mode` line, no double parentheses, a
sensible probe count). A dedicated `TargetParseError` variant for pair parsing so the
message reads as a sentence.

## Sequencing and cost

| phase | value | rough cost |
|---|---|---|
| R1 integrity | highest — restores the central guarantee | half a day |
| R2 resume provenance | high — closes the last brief question | half a day |
| R3 failure coverage | high — prevents recurrence | one day |
| R4 complexity | medium — pays back on the next change | half a day |
| R5 surface + drift | medium | half a day |
| R6 polish | low | an hour |

R1 first is not negotiable: C1 and C2 mean the record can currently misreport a failed
run as a clean one, which is the one thing this tool exists to prevent.

## Explicitly not proposed

Adaptive concurrency, built-in compression, multi-proxy, and the deferred platforms all
remain deferred with their existing revisit triggers. Nothing in this review changes the
case for them.
